# GH13-CBM HMM Workflow

This repository contains a standalone, corrected implementation of the Python workflow used
to search predicted proteins with dbCAN family profile hidden Markov models and to evaluate
family-specific operational bit-score cutoffs. It was separated from the research database
and application so the computational method can be inspected, tested and reused without
publishing metagenomic sequences or candidate records. The historical production invocation
and its complete reference manifest were not available for inclusion, so this release does
not claim byte-for-byte regeneration of earlier project outputs.

The software reports **sequence evidence for similarity to a profile HMM**. A GH13-family
match does not by itself establish alpha-amylase activity. A CBM-family match does not
demonstrate substrate binding. Neither result establishes cold activity, alkaline stability,
detergent compatibility or any other biochemical property. Those conclusions require
additional sequence, structural and experimental evidence.

## Repository scope

Included:

- profile-HMM scanning through PyHMMER;
- explicit target- and domain-reporting thresholds plus the independent-domain decision
  threshold;
- HMM alignment coverage and domain-coordinate calculations;
- construction of deterministic labelled reference samples from user-supplied resources;
- exact bit-score cutoff calibration and robustness calculations;
- complete confusion matrices and Wilson 95% confidence intervals;
- application of family-specific operational cutoffs;
- checksums and machine-readable run manifests;
- unit tests that contain no biological sequences.

Excluded:

- metagenomic protein or nucleotide sequences;
- sample names, candidate identifiers and candidate-level annotations;
- raw reads, contigs, gene predictions and database exports;
- CAZy and UniProt reference sequences;
- dbCAN profile HMM files and DIAMOND databases;
- project-specific cutoff files and derived research results.

The HMM profiles are third-party scientific resources. They are not generated by this code
and are not covered by this repository's MIT licence. Obtain the appropriate dbCAN release
from the official dbCAN distribution, record its release and checksum, and comply with the
provider's terms.

## Method summary

1. Predicted protein sequences are supplied in FASTA format outside the repository.
2. One or more profiles are loaded from a user-supplied HMMER file.
3. PyHMMER `hmmsearch` compares each selected profile with the protein collection.
4. HMMER's target and conditional-domain reporting boundaries are configured separately and
   permissively. A domain is retained only when its independent-domain E-value and aligned
   fraction of HMM match states pass the stated decision boundaries.
5. Family membership is represented by the profile name, bit score, E-value, HMM coverage
   and alignment coordinates. A separate annotation step is required to infer enzyme class.
6. When a family-specific cutoff is calibrated, each labelled reference contributes its
   best domain bit score or a score of zero if no domain is reported. The implemented
   selection rule chooses the lowest bit-score threshold that admits zero observed
   calibration negatives.
7. Cutoff performance is reported as counts and rates, with the numbers of positive and
   negative references and Wilson 95% confidence intervals.

The cutoff procedure is an **internal calibration** against its selected reference set. It
is not independent validation, because the same examples determine and evaluate the
boundary. A claim of external predictive performance requires a held-out reference set that
did not influence model choice, reference sampling or threshold selection.

See [Methods](docs/METHODS.md) for the full computational definition and
[Scientific audit](docs/AUDIT.md) for corrections and remaining limitations.

## Installation

The release environment uses Python 3.12, PyHMMER 0.11.0 and Requests 2.34.2. Create an
isolated environment before installation:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[dev]'
```

Run the checks:

```bash
ruff check .
ruff format --check .
pytest
```

## Command-line use

### Search protein sequences

```bash
gh13-cbm-hmm scan \
  --proteins /path/to/predicted_proteins.faa \
  --hmms /path/to/dbCAN.hmm \
  --profile GH13 CBM20 CBM34 CBM37 CBM41 CBM48 CBM69 \
  --target-reporting-evalue-threshold 10 \
  --domain-reporting-evalue-threshold 10 \
  --independent-domain-evalue-threshold 1e-15 \
  --minimum-hmm-coverage-percent 35 \
  --evalue-search-space 875 \
  --cpus 4 \
  --output outputs/domain_hits.tsv
```

`--evalue-search-space` sets HMMER's `Z` value and is mandatory. For the audited dbCAN file,
`875` is the number of profiles in the complete library and provides the database-wide value
required for the intended hmmscan-equivalent convention, even when only selected profiles are
loaded. Determine and record the correct value for any other HMM release. Bit scores do not
depend on `Z`; E-values do. The command writes a JSON manifest next to the result table with
input checksums, versions, parameters, profile names and the output checksum.

The default decision rule matches the applied project rule: independent-domain E-value no
greater than `1 × 10⁻¹⁵` and aligned HMM coverage of at least `35%`. The two HMMER reporting
thresholds default to a permissive value of `10` and are not decision boundaries. A later
observed bit-score boundary must not be described as the original screening rule.

### Calibrate an operational score cutoff

Prepare a tab-separated score table with these columns:

| Column | Definition | Unit |
| --- | --- | --- |
| `profile_name` | Exact HMM profile name | none |
| `class_label` | `positive`, `hard_negative`, `easy_negative` or `negative` | none |
| `domain_bit_score_bits` | Best score for the profile; use zero when no domain was reported | bits |

Supply one row per unique reference sequence. This compact command-line schema contains no
reference identifier or checksum, so it cannot detect duplicated input rows; deduplication
must be completed and documented before the score table is created.

Then run:

```bash
gh13-cbm-hmm calibrate-score \
  --scores /path/to/labelled_scores.tsv \
  --family CBM20 \
  --comparison-threshold-bits 67 \
  --robustness-delta-bits 5 \
  --output outputs/CBM20_calibration.json
```

The report includes the full confusion matrix at each evaluated threshold. Field names spell
out correctly detected positives, missed positives, incorrectly accepted negatives and
correctly rejected negatives. Sensitivity, specificity and their Wilson 95% confidence
intervals are proportions from zero to one. Thresholds and score offsets are in bits.

The selected cutoff is the lowest evaluated bit-score threshold with zero observed false
positives in the calibration negatives. “Zero observed” is literal: it does not prove that
the population false-positive rate is zero. The report retains the negative sample size and
its confidence interval so the precision of the estimate remains visible.

For a fully programmatic reference calibration, `gh13_cbm_hmm.references.build_pools()` and
`labelled_set_for_family()` construct the labelled classes, and
`gh13_cbm_hmm.calibration.calibrate_profile()` scores them with one supplied profile. The
returned reference manifest contains class labels, accessions and sequence checksums, but no
sequence content; archive that generated manifest with the analysis rather than committing
it to this code repository.

### Apply calibrated cutoffs

```bash
gh13-cbm-hmm apply-cutoff \
  --hits outputs/domain_hits.tsv \
  --cutoffs outputs/CBM20_calibration.json \
  --cutoffs outputs/CBM41_calibration.json \
  --output outputs/domain_hits_classified.tsv
```

Each domain-hit row is labelled `passes_operational_cutoff`,
`below_operational_cutoff` or `uncalibrated_family`. Add `--require-calibrated` to stop if a
profile has no supplied cutoff. These labels describe the score rule only; they are not
claims of validated activity or domain function.

Detailed schemas and coordinate conventions are given in
[Input and output specification](docs/INPUT_OUTPUT.md).

## Reproducibility requirements

Archive the following with each scientific run:

- the immutable input and HMM-file checksums;
- the HMM database name, release and retrieval date;
- all selected profile names;
- PyHMMER, package and Python versions;
- target- and domain-reporting E-value thresholds and the independent-domain decision
  threshold;
- the explicit HMMER `Z` value and its justification;
- minimum HMM coverage in percent;
- processor count and execution command;
- reference queries, accession snapshot and class definitions used for calibration;
- random seed and requested reference counts;
- the invalid-reference policy and number excluded, if any;
- output checksum and the unrounded cutoff value in bits.
